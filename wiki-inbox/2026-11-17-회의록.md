- **발표 항목 구성**: 선향·효빈·인정이 각자 정리한 내용을 합쳐 1~14번 항목으로 구성하고, 8번을 기준으로 **위쪽(1~8, 프로토타입 포함)은 효빈 / 아래쪽(9~14, 기술 내용)은 선향**이 맡기로 함. 아직 정해지지 않은 항목은 노란색으로 표시해 회의 전까지 채워 오는 방식으로 진행함.
- **프로토타입 공개 방식**: QR로 청중에게 공개하는 방안과 캡처 화면만 보여주는 방안을 논의함. AI로 만든 프로토타입은 완성도가 아쉽고 시간이 하루뿐이므로 **캡처로 삽입**하되, 기능 설명 옆에 해당 화면을 함께 띄워 **"이 화면에 이 기능이 들어갔다"를 연결해 설명**하는 방식으로 결정함(효빈 제안). 기능 우선순위는 그만큼 간략하게 설명하기로 함.
- **인정 역할**: 원고 파일 작성은 없는 대신 확정된 플로우를 기반으로 **유스케이스 초안**을 작성하고, 리허설에도 참여해 디자인 피드백을 바로 반영하기로 함.

### 2. 🧠 숙제 공유: LLM API 및 RAG 학습, 서비스 내 RAG 적용 범위
- **API 연동·대화 기억**: 요청 시 시스템 메시지와 user/assistant 메시지를 번갈아 보내고, 응답은 content 텍스트로 받는 구조(POST 1회 요청 → 응답)로 모두 동일하게 이해함. 대화 기억은 이전 대화를 **전부 이어 붙여 다시 전송**하는 방식으로 유지됨을 확인함.
- **RAG 파이프라인**: 사전 준비 단계(청킹 → 벡터화 → 벡터 DB 저장)와 질문 답변 단계(질문 검색 → 상위 k개 → 프롬프트 구성)로 나뉘고, 앞 단계의 출력이 다음 단계의 입력이 되는 단방향 구조임을 정리함.
- **서비스 내 RAG 필요 여부**: 질문 Set의 예/아니오 분기를 따라가면 위반 법령이 규칙처럼 명확히 결정되므로 **법률 근거 제공에는 RAG가 필요하지 않다**는 의견으로 모임(선향·효빈·인정 공통).
- **RAG가 필요한 지점**: 유형 선택 시 "잘 모르겠어요 → 주관식 입력"을 LLM이 해석해 후보 유형과 연결하는 부분에서만 쓰기로 확정함. 인정은 법 조항을 내 상황에 융통성 있게 해석해야 하는 경우에 RAG가 쓰일 수 있으나, 실습상 단순 파이프라인은 검색 성능이 낮아 **성능 개선 노력이 필요**하다는 점을 공유함.
- **lexguard MCP 검토**: AI가 한국 법령 API를 실시간 조회하게 해주는 MCP를 조사함. 모든 법령을 다뤄 범위가 지나치게 크고, 그대로 쓰면 졸업 프로젝트의 직접 구현 비중이 줄어드므로 **API 조회 구조를 참고하는 용도로만 활용**하고, 우리는 **필요한 조문만 저장**하기로 결론 냄.

### 3. 🖼️ 프로토타입 비교 및 화면 구조 결정
- **선향 프로토타입**: 기능을 최소화(Must~Should)했고 하단바는 홈·내 사건·설정. 근로계약서를 처음부터 받지 않고 간단한 정보만 질문하며, 증거를 **공통 증거 / 유형별 증거**로 나눠 수집하고, 사건 상세에서 **내가 등록한 증거(원본)와 서비스가 정리해 준 증거를 분리**한 점이 특징임.
- **효빈 프로토타입**: 시작 화면 → 진단 → 정보 사용 동의 → 계약서·입금내역 업로드 → AI 확인 → 추가 질문 → 근무 캘린더 → 진단 결과 → 증거 수집(위·변조 책임 고지 포함) → 해결 방법 → 내보내기 → 사건 정리(사장님 반응 연습·결과 기록)의 흐름임.
- **인정 프로토타입**: 하단 4탭(홈/증거/문서/내 사건), 질문을 단계별 페이지로 분리, 마스킹 범위 선택, 근무 캘린더, 진단 결과 색상 구분(기준 확인=파랑, 조건부 판단=초록, 추가 확인 필요=노랑), 대응 방법 A/B/C 비교, 증거 팩 편집 등이 특징임.
- **하단바**: 세 명 모두 홈·내 사건이 공통이므로 **하단바는 홈과 내 사건만** 두기로 함. 증거·문서 탭은 하단에서 빼고 **내 사건 상세 안에서 이어지도록** 함.
- **내 사건 상세 구성**: 사건 개요(신규 추가), 진행 단계, 진단 결과, 근로 정보·근무 캘린더, 증거 정리, 선택한 대응(변경 가능), 문서 초안·증거 팩, 내보내기, 결과 기록(Should)을 담기로 함. 인정 프로토타입의 사건 정보 구성을 차용함.
- **진행 단계 UI**: 클릭 가능하다는 것을 사용자가 인지하기 어려우므로 **탭 형태 + 1·2·3단계 순서 표시**로 보이게 하고 "진행 단계" 문구도 수정하기로 함. **진단 결과는 수정 불가**(진단이 바뀌면 뒤 단계가 모두 바뀌므로), 다시 받고 싶으면 **재진단** 방식으로 하며, 진단 결과 보기는 플로우 재진입이 아닌 **결과서 형태의 단독 화면**으로 보여줌. 증거 정리부터 결과 기록까지는 토글/병렬 탭으로 구성함.
- **선택한 대응·문서 초안**: 선택한 대응과 문서 초안이 겹치므로 별도 "선택한 대응" 페이지는 두지 않고 **하나의 섹션 카드로 통합**함. 진행 절차·예상 기간·비용 등 개요는 문서 영역 상단에 간략히 넣고, 초안과 증거 팩도 같은 화면에서 다루며, 대응 변경 시에는 대응 방법 탭으로 이동함.
- **사건 추가 진입점**: 홈과 내 사건 **두 곳 모두**에서 가능하도록 함.
- **홈 화면**: 처음 진입 시 환영하는 화면이 필요하다는 의견에 따라 **홈은 유지**하되, 진행 중인 사건 1건 요약과 응원 메시지 정도로 간단히 구성하고, 구현 후 쓸모가 없어 보이면 삭제하기로 함.
- **프로토타입 범위**: Must~Should까지만 구현하고, 사장님 반응 연습은 제외함(Could).

### 4. 🔀 서비스 플로우 논의 (근로계약서 시점, 근무 캘린더)
- **쟁점**: 선향은 근로계약서를 증거 수집 단계에서 받았고, 효빈·인정은 유형 선택 직후 받음. 근로계약서를 먼저 요구하면 찾으러 가다가 이탈할 수 있고, 질문으로 받으면 입력 부담이 생긴다는 양쪽 문제를 확인함.
- **결정**: **유형 선택 직후 2번째 단계로 근로계약서 업로드**를 두되, **"업로드하면 기본 정보를 자동으로 채워드려요, 귀찮으면 업로드하지 않아도 돼요"**로 안내해 선택 사항으로 함. 업로드하지 않으면 질문 Set에서 시급·근무 기간 등을 묻고, 정보 사용 동의도 함께 받음.
- **근무 캘린더**: 업로드 즉시 수정하는 방식이 아니라 질문 Set을 마친 뒤 만들어 수정함. 근로계약서가 없으면 **질문 Set로 캘린더를 생성**하고, 있으면 OCR로 추출한 값으로 만듦(추출값은 사용자가 확인·수정).
- **근무 캘린더 기능**: **월간 보기만** 구현(주간 불필요). 날짜 클릭 시 **근무 상세 팝업**(근무 시간·휴게 시간), 카톡 근무 지시 캡처 등 **일자별 증거 첨부**, **총 근무 시간 정리**, **예상 급여 계산**을 제공함. 급여 미수령 판단을 위해 **입금받은 날짜를 클릭해 입금 내역을 올리는 방식(OCR)**을 쓰고, 주급 지연 여부도 확인할 수 있게 함.
- **세미 증거 수집 단계**: 근무 캘린더가 사실상 입금내역·카톡을 받는 세미 증거 수집 단계로 기능함. 사용자가 증거 수집 단계로 인지하지 못하므로, 진단 결과에서는 "어떤 증거가 부족해요"가 아닌 **"이런 정보가 더 필요해요"** 정도로만 안내함.
- **최종 확인 단계 삭제**: 근무 캘린더에서 사용자가 오래 머물며 이미 수정을 마치므로 입력 내용 최종 확인 페이지는 **삭제**하고 바로 진단 결과로 넘어가기로 함.
- **진단 결과**: 근거 조항, 시효 안내, 더 필요한 정보 안내를 포함함.
- **증거 수집**: 공통 증거와 쟁점별 증거를 분리해 수집하고, "있어요 / 없어요" 선택에서 "없어요"는 대체 자료를 안내하며, **위·변조 책임 고지**를 함께 넣음.
- **증거 출처 라벨링 삭제**: 법정까지 가지 않는 경우가 많고, 캡처만 봐도 출처가 파악되며, 모든 증거에 요구하면 부담이 커지므로 삭제함.
- **기억 기반 정리 → `Could`로 하향**: 구두 진술이 필요한 항목(계약서 미교부 등)은 해당 질문에서 바로 받으면 되고, 나머지는 명확한 증거가 필요해 효용이 낮다고 판단함.
- **증거 후 판단 → 판단 후 증거**: 인정 안은 증거를 먼저 모으고 판단하는 흐름이었으나, 확정 플로우는 **진단 후 증거 수집**이므로 이에 맞춰 조정함.

### 5. 🛠️ 기술 적용 범위
- **규칙 기반**: 질문 답변 → 위반 가능성 진단, 사업장 조건(5인 이상 등) 경로 분기, 받아야 할 금액·차액 계산, 청구 기한(시효) 계산, 근로계약서 값 → 근무 캘린더 변환, 관련 조문 표시(조문 DB).
- **구조화 데이터**: 유형별 꼬리 질문, 쟁점별 필요 증거 및 대체 자료 연결.
- **OCR**: 근로계약서(시급·급여일·근무 시간), 입금 내역 사진(입금일·금액) 추출. 추출값은 사용자가 확인·수정하며 입력 부담을 최소화함.
- **마스킹**: AI에 보내는 모든 데이터(텍스트·이미지)에 적용하며, 외부 LLM 호출 전 단일 관문으로 둠.
- **LLM**: 초안 작성(사장님 메시지, 상담서, 신고서), 주관식 상황 입력 → 사실 추출·후보 유형 제안(확정은 사용자·규칙), 기억 기반 증거 정리 도우미(Could), 사장님 대응 연습(Could).
- **LLM 적용에서 제외**: 카톡 대화 내용 해석·판단(증거 후 판단 플로우 기준이었음), 부족한 정보 판단 및 추가 요청(확정 플로우에서 불필요).
- **공통 원칙**: LLM은 법적 판단을 독립적으로 하지 않고, 마스킹 후에만 AI에 전송하며, 자동으로 읽은 값은 사용자가 고칠 수 있음. 한 문장으로 **"판단과 계산은 규칙, 입력은 OCR, 쓰기와 정리는 LLM, 질문과 증거 목록은 구조화 데이터, AI 전송 전에는 항상 마스킹"**.

### 6. ⚖️ 법률 정보 판단 파이프라인 및 법 개정 대응
- **필요한 법률 정보 4가지**: 위반 요건·적용 조건·예외(문제 진단), 계산 기준값(받아야 할 금액), 시효·기간(청구 기한), 구제 절차·기관(해결 경로).
- **저장 방식**: 유형·조문이 정해져 있고 매번 API를 호출하면 비용이 발생하므로 **미리 저장**함. 조문 시트(국가법령정보센터 Open API로 사전 수집), 규칙 시트(상황 → 결과 → 근거 조문), 기준값 시트(최저임금 등을 고용노동부·최저임금위원회 발표 기준 수작업 입력), 기관 시트(기관·신고 방법·접수 양식 수작업 입력)로 구성함.
- **판단 흐름**: 입력·업로드 자료에서 사실관계 추출 → 적용 조건 확인(부족하면 추가 질문) → 규칙표로 판정(if문) → 근거 조문 번호로 조문 DB에서 원문 조회 → 쉬운 말 설명 → 결과 카드 조립(판정·적용 법령·판단 근거·필요 증거).
- **확실성 3단계(인정 제안)**: 명확한 기준(법령에 명시된 요건·계산식), 조건부 판단(사용자 진술이나 추가 사실 확인 필요), 판단 보류(핵심 정보 부족·사실 충돌 시 추가 질문으로 연결).
- **쉬운 말 설명 방식**: 인정은 법적 일관성을 위해 미리 쓴 문구를, 효빈은 사용자 상황에 맞춘 LLM 생성을 제안함. **조문별 필수 설명은 시스템 메시지로 고정하고, LLM은 사용자 상황에 맞게 풀어쓰는 역할만 하는 절충안**으로 확정함. 판정과 근거 조문은 LLM이 바꿀 수 없게 함.
- **법 개정 대응**: 값이 바뀌는 경우(최저임금 등)는 **값 + 적용 기간(시작~종료일)**으로 저장하고 해가 바뀌면 새 행을 추가함(기존 행 삭제 안 함). 조문이 바뀌는 경우는 주기적으로 API로 조문을 받아 저장본과 비교(diff)하고, 차이가 있으면 담당자에게 슬랙·디스코드 알림을 보내 **사람이 검토한 뒤 반영**함.
- **버전 관리 원칙(효빈·인정 보완)**: 덮어쓰지 않고 **추가**하며 법령마다 시행일을 저장함. **사건 발생 시점에 맞는 조문·기준값을 적용**하고, 사건 진행 중 법이 바뀌면 사용자에게 고지하고 승인한 뒤 변경함.
- **사용자 표시 및 검증**: 결과 카드마다 "○○년 ○월 기준"을 표시하고 법 개정 가능성을 고지함. 규칙·계산을 바꾸면 테스트를 재실행하며, 이를 위해 **규칙·계산과 근거 조문 ID를 연결**해 두기로 함.

### 7. 🔒 개인정보 보호와 증거력
- **원칙**: 증거로 쓰는 것은 **원본**, AI와 외부로 나가는 것은 **마스킹한 사본**. 정리본·계산서는 증거가 아닌 전달용이며, 표현은 "증거를 만들어드려요"가 아니라 **"증거를 모으고 정리하는 걸 도와드려요"**로 함.
- **민감도별 처리**: 높음(주민번호·계좌번호·연락처)은 항상 가려서 AI에 보내고 서비스에 별도 저장하지 않음(연락처는 계정·알림용 저장 가능). 중간(사용자·사장님 이름, 사업장명·주소)은 AI에 보낼 때 가렸다 복원해 암호화 저장(초안·신고서, 관할 노동청 안내에 필요). 낮음(근무 날짜·시간, 시급, 금액)은 필요한 값만 추출해 저장하고, 증거 파일·주관식 원문은 원본 그대로 암호화 저장함.
- **저장소 분리**: 원본 저장소(수정 불가·추가 업로드만, 업로드 시각과 SHA-256 해시 기록, 외부 제출 시 원본 그대로 전달), 마스킹본 저장소(AI 전송용), 분석 데이터 저장소(OCR→LLM 결과를 원본과 분리, 사용자 수정은 별도 기록). **AI가 만든 정리본에는 AI 사용 고지 필수**.
- **마스킹 범위 선택권**: AI 전송용과 외부 공개용(상담 게시판 등)을 나누어 논의함. 인정은 포맷이 정해진 정보는 OCR로 자동 마스킹하되 인식하지 못하는 패턴·이미지가 있을 수 있어 사용자 추가 지정이 필요하다고 설명함. 결과적으로 **AI 전송 시와 외부 내보내기 시 동일한 규칙으로, 사용자에게 마스킹 범위 선택권을 주기로 확정**함. 내보낼 때는 필요한 정보만 선택하게 함.
- **고민 중인 사항**: 원본 **수정 불가**의 장단점(위·변조 가능성은 줄지만 사용자 편의 제약)을 추가로 논의하기로 함. 원본 보존·개인정보 보유기간 정책, 삭제 요청 시 원본·분석 결과·복원용 대응표 동시 삭제(백로그 S5.2 연결)는 정책으로 정해야 함.

### 8. 👥 역할 분담, 마일스톤, 수익 모델 (2부)
- **개인정보 범위 합의**: 마스킹 선택권을 AI 전송·외부 전송에 **일관 적용**하기로 함(효빈은 원천 차단을 위해 위험 정보는 전부 마스킹 후 전송하자는 입장, 선향은 선택권 부여 입장으로 결국 일치).
- **역할 분담**: 인정의 역할에 **서비스 보안 취약점 분석·점검을 추가 확정**함(악성 파일 업로드, 저장 경로 노출, 타 사용자 사건·증거 접근 가능 여부 등). 인정은 시나리오 기반 서비스 흐름 평가(E2E 테스트, 정량 평가)도 중간·기말·최종 발표에서 어필할 수 있는 영역으로 제안함. 백엔드는 Java로 개발하고, 마스킹·OCR 등 **파이썬 친화 기능은 인정이 별도 서버로 분리해 담당**함.
- **Google Colab**: 교수님이 무료로 나눠주는 계정을 팀 공용으로 쓰기 위해 인정이 공용 구글 계정(푸딩랩 2026)을 만들고, 선향이 신청 폼을 작성하기로 함.
- **마일스톤 초안**: 에픽 → 유저 스토리 → 태스크로 쪼개고 완료 기준을 두었으며, 개발 일정을 5개 구간으로 나눠 유저 스토리를 배분함. 빠르게 만든 초안이므로 **발표 자료에는 "추후 점검 필요"로 표기**하고, 누락·우선순위 오류를 같이 점검하기로 함. 기술 스택 초안은 모두 동의함.
- **예상 질문 및 수익 모델**: 예상 질문은 두 개씩 작성했고, 수익 모델 질문 답변을 논의함. 광고는 개인정보·법률 서비스 특성상 부적합하고 사용자 직접 과금은 사용 저하가 우려되므로, **일부 기능 소액 유료화**(증거 팩 PDF 정리본 1,000원 정도), **노무사 연계 시 입점비·수수료**, **공공기관·지자체 협력**을 방안으로 제시하기로 함. 이번 발표에서는 "이런 모델을 고려하고 있다" 수준으로 답변하고, 창업 대회 등으로 이어지면 구체화하기로 함.

## 🏆 회의 결과

### 1️⃣ 🔀 서비스 플로우 및 화면 구조 확정
- **플로우**: 1) 유형 선택 → 2) 근로계약서 업로드(선택) → 3) 질문 Set → 4) 근무 캘린더(세미 증거 수집) → 5) 진단 결과 → 6) 증거 수집 → 7) 대응 방안 선택 → 8) 문서 초안/증거 팩
- **하단바**: 홈 + 내 사건. 증거·문서는 내 사건 상세 안에서 접근
- **내 사건 상세**: 사건 개요, 진행 단계(탭형·순서 표시), 진단 결과(수정 불가·재진단), 근로 정보·캘린더, 증거 정리, 대응 방법·문서 초안·증거 팩 통합, 내보내기, 결과 기록
- **기타**: 사건 추가 진입점 2곳(홈·내 사건), 홈은 유지하되 간소화, 최종 확인 단계·증거 출처 라벨링 삭제

### 2️⃣ 📊 유형별 구현 범위 (Must / Should / Could)
- **Must**: 1~4순위 (근로계약서 미작성·미교부 / 주휴수당 미지급 / 최저임금 미달 / 임금체불·임의 공제·일방적 삭감)
- **Should**: 5~6순위 (연장·야간·휴일·연차 수당 / 부당해고)
- **Could**: 7~8순위 (휴게시간 미부여 / 폭언·괴롭힘·성희롱)
- 질문 Set은 객관식으로 구성하며, 주관식 입력은 "잘 모르겠어요" 선택 시 LLM이 후보 유형을 제안하는 방식으로 포함함
- **기능 조정**: 기억 기반 정리 도우미 → `Could`로 하향, 사장님 대화 연습 → `Could`(프로토타입 제외), 결과 기록 → `Should`

### 3️⃣ 🧩 기술 적용 원칙
- 판단·계산은 **규칙**, 입력은 **OCR**, 쓰기·정리는 **LLM**, 질문·증거 목록은 **구조화 데이터**, AI 전송 전에는 **항상 마스킹**
- RAG는 법률 근거 제공에는 쓰지 않고 **주관식 답변 ↔ 유형 연결**에만 적용
- 쉬운 말 설명은 **조문별 고정 문구(시스템 메시지) + 사용자 상황 맞춤 LLM 풀어쓰기**, 판정·근거 조문은 LLM이 변경 불가
- 필요한 조문만 저장(lexguard MCP는 구조 참고용), 법 개정은 **추가 방식 버전 관리 + 사람 검토 후 반영**, 사건 발생 시점 기준 법령 적용
- 증거 원본 / 마스킹본 / 분석 데이터 **저장소 분리**, 마스킹 범위 **사용자 선택권(AI 전송·외부 내보내기 일관 적용)**, **AI 사용 고지 필수**

- **역할**: 인정 — 유스케이스 초안, 보안 서비스 취약점 분석·점검, 파이썬 기반 기능(AI·마스킹·OCR) / 선향·효빈 — 발표 담당
